# Screens

Every screen of the desktop application (docs/PLAN.md section 7, phase 3),
the rendering it follows (`design/INDEX.md`), the worker commands it sends,
and where it departs from the rendering and why. docs/DECISIONS.md D27
holds the recommendations this inventory rests on. Rendering numbers are
those of `design/INDEX.md`: 01 create or restore, 02 dashboard, 03 batch
send, 04 activity, 05 settings, 06 explorer, 07 block, 08 tag.

The **PR** column says which of D27's four pull requests (item 16) builds
the screen: (a) the first-run screens and the shell, (b) the wallet, (c)
activity, settings and recovery, (d) the explorer. Every built screen has
a screenshot in `design/screenshots/` with the same name.

## The states that fail closed (docs/PLAN.md section 4.9)

Each of these gets a designed screen, never an OK dialog. Each says what
happened in a slim banner, which opens into a summary in Tawara's words
with its common causes, and from there into the library's own page,
whole (D28; D27 item 13 for how the page is shown):

| state | where it is shown | what the person can do there |
|---|---|---|
| an account diverged from the chain | account state panel (W7, `diverged`) | read the library's report; open account recovery (W12). Nothing on this screen moves an index |
| reserved and not settled | account state panel (`outstanding`) | wait: the wallet settles it by itself once a read shows it landed (D38); re-sign the same spend (W8); submit a saved artifact (W9) |
| a spend that landed and is not yet settled | account state panel (`landed`) | Settle, the fallback for a settle the wallet could not make by itself (D38) |
| a reservation that can no longer be accepted | account state panel (`dead`) | read why (balance moved, or its block-to-live passed); no Settle is offered, since a dead reservation never settles (D38) |
| an account emptied to zero | account state panel (`not found`) | read the library's reading of "account not found"; receive to it again |
| a spend between submission and settlement | sent page (W6) | read the three facts; save the artifact; the wallet settles it by itself once a read shows it landed (D38) |

The three facts are never softened: a submit is a socket write, not a
verdict; the node's validation has never run offline; the signed
transaction can be lost, so the sent page offers to save it (D27, item 5).

## Compact layout (phones)

The layout is chosen by the window's logical width: compact below 600 logical
pixels, and the desktop's layouts (D27, item 9) from there up. The one exception
is W1's sections, which follow whether the app runs in a phone shell rather than
the width, so a phone held sideways shows the same ones (D39, item 5). A phone
starts at 360 wide until the window reports its size. The narrowest width
supported is 360: at it nothing is cut off and nothing scrolls sideways. The safe
area the system reports (the status bar, the home indicator and the on-screen
keyboard) pads the root of every layout, so a phone held sideways, which is wider
than 600, keeps its notch clear; while an iPhone reports no inset at all, the
root is padded 64 above and 48 below. When the keyboard comes up, the page
scrolls the focused field above it (D32 item 10 (b)). A phone held sideways, 600
to 1023 wide, draws the desktop's medium layout, which is not checked at those
widths.

The wallet's shell in the compact layout (`crates/app/src/screens/wallet.rs`):

- a bar at the top, 56 logical pixels tall: the wordmark, the node chip (the
  node's dot and its chain tip, or a dash, which goes to the node screen while
  the wallet is idle), and Lock;
- the page between 16-pixel margins, scrolled as one page;
- a bar at the foot, 56 pixels tall, with the six items of the sidebar, each
  an icon over its name, sharing the width; it is not drawn while the keyboard
  shows;
- a page's actions sit beneath its title and wrap onto the next line when they
  do not fit (the page decides which: W1 drops Receive and Send, since they are
  tabs);
- there is no back stack: the sub-pages (W3, W7, W8, W9, W12, E2 to E5) are

  Android's Back keeps its meaning (`Host::back`).

Every screen has a compact form. Tables become stacked rows, cards keep 16
pixels of padding, and a long token (a destination, a hash, an id, an amount)
wraps at its glyphs. The balance is the exception: its figure (in MCM, its
whole part, before the point; the decimals may wrap below it) is set at the
largest size, 56 pixels at most, that keeps it on one line in its card, so a
nanoMCM balance is set smaller (the sample's, 12,395,402,118,000, at 30 pixels
at 360; D32 item 10 (b)). An MCM balance under a million keeps 56; from seven
whole digits one can be set smaller (4,444,444 at 53 at 360). Acting on a row or a card is by release, so
a drag that starts on it scrolls the list (D32 item 10 (d)). A drag that starts
on a button or a field does not scroll the page, since the fork's button and
field capture the press; on the forms a drag starts on a label or a gap. Beside
each field a person pastes into (a destination, the signed bytes, the recovery
phrase) stands a Paste button, which replaces the field's text with the
clipboard's (D32 item 10 (g)).
